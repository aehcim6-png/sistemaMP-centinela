SistemaMP Centinela — documentación

Arquitectura del Sistema

Explicación textual de cómo está construido el sistema. Para la versión visual, ver el plano interactivo.

Resumen en una frase

Una página web (sin backend propio) que guarda cada cambio en tres lugares al mismo tiempo — este computador, Supabase en la nube, y opcionalmente una carpeta de respaldo — para que nunca dependa de un solo lugar ni de que haya internet.

Las piezas

1. El frontend — index.html + modules/

Todo el sistema es HTML/CSS/JavaScript plano, sin framework (nada de React, Vue, etc.) y sin proceso de compilación de lógica (Vite solo empaqueta y copia archivos, no transforma el código JS). Se decidió así a propósito: es más fácil de mantener por una sola persona sesión a sesión que introducir un framework nuevo a mitad de camino.

  • index.html (~3.300 líneas) — el esqueleto: la barra de navegación, el login, el arranque de la aplicación, y la infraestructura compartida entre pestañas que no encajaba en un módulo propio (autoguardado a carpeta local, auditoría, MFA, gestión de usuarios).
  • modules/renders/*.js (39 archivos) — un archivo por pestaña o sub-pestaña del sistema. Cada uno define window.render<Tab> más los botones/formularios exclusivos de esa pestaña. Son scripts planos, no módulos ES — comparten el mismo espacio de variables globales que el resto del sistema, a propósito.
  • modules/store.js — el motor de sincronización (ver sección 3).
  • logic.js — funciones de cálculo puras: fechas de próxima mantención, disponibilidad, similitud de materiales, etc. Es el único archivo con pruebas automatizadas (181 casos, corren con Vitest).

2. Dónde vive — Vercel

Vercel sirve los archivos estáticos (no hay servidor propio corriendo en ningún lado). Cada push a la rama main dispara un build (vite build) y un despliegue nuevo automático. vite.config.js copia logic.js, vendor/*.js, toda la carpeta modules/ y toda la carpeta docs/ al resultado del build, ya que Vite por diseño no "empaqueta" scripts que no son módulos ES.

3. El motor de sincronización — modules/store.js

Todo el sistema lee y escribe datos a través de dos únicas funciones: S.g(categoria) (leer) y S.s(categoria, valor) (guardar). Ninguna pantalla llama directo a Supabase — todas pasan por acá, lo que permite que el resto del sistema (634 llamadas repartidas en las 39 pestañas) nunca necesite saber cómo ni dónde se guardan realmente los datos.

Al llamar S.s(categoria, valor) ocurren, en este orden:

  1. localStorage — se escribe de inmediato, siempre, funcione o no internet.
  2. Supabase — si la categoría es una de las 31 tablas reales, se envía sin demora un upsert más un delete de filas eliminadas — pero antes se hace un chequeo de conflicto (ver más abajo).
  3. Carpeta de respaldo (opcional) — si alguien conectó una carpeta local, 5 segundos después del último cambio se escribe ahí un SistemaMP_Datos.json con todo. Es "por computador": cada equipo que quiera este respaldo tiene que conectar su propia carpeta.

4. Detección de conflictos

Antes de escribir en una tabla real, el sistema compara "lo que esta pestaña creía que había antes" contra "lo que hay AHORA mismo en el servidor". Si son iguales, guarda normal. Si son distintos, el guardado se cancela, la pantalla se refresca con lo más reciente, y aparece un aviso. Nunca se sobrescribe en silencio el trabajo de otra persona.

5. Autenticación y roles — Supabase Auth

  • Login: correo + contraseña. Si la cuenta tiene MFA activado, pide el código de 6 dígitos DESPUÉS de validar la contraseña, nunca antes.
  • Roles: admin u operador, guardado en user_roles. El rol oculta/muestra botones (cosmético) y aplica Row Level Security real en Postgres — 4 tablas mixtas tienen además un trigger que bloquea a un operador que intente cambiar columnas reservadas a admin, aunque manipule el navegador.
  • Gestión de usuarios: pasa por una única Edge Function (crear-operador), el único punto del sistema con privilegio elevado.

6. Estructura de datos en Supabase

~31 tablas, una por categoría, más 6 "singleton" de configuración. El mapeo vive en TABLA_REAL/TABLA_SINGLETON dentro de modules/store.js. El schema está versionado como código en supabase/migrations/*.sql.

7. Límites y respaldo

Plan gratis de Supabase: 500 MB de base de datos (hoy ~22 MB, 4.4% usado), 5 GB de ancho de banda al mes, se pausa solo tras 7 días sin uso (se reactiva con un clic, sin perder nada, hasta 90 días después). El límite más cercano en la práctica no es el tamaño de los datos sino el ancho de banda, porque el sistema baja toda la base al iniciar sesión.

Respaldo paralelo: la carpeta local conectada (JSON cada 5s) es la primera red de seguridad fuera de Supabase. También existe "Backup manual" en Configuración.

Si Supabase dejara de existir (escenario extremo): cada navegador tiene una copia completa en localStorage, y el JSON de backup permitiría reconstruir los datos en otro backend.

8. Monitoreo de errores — Sentry

Cada error real de JavaScript en producción queda registrado en Sentry con el usuario y la acción que lo disparó. El SDK está vendorizado en vendor/sentry.min.js (mismo criterio que jspdf/qrcode/xlsx: nada por CDN en tiempo de ejecución) y se inicializa lo más temprano posible en <head>. Solo captura errores y breadcrumbs — sin tracing de performance ni session replay. Configuración → "🐞 Monitoreo de errores" (solo admin) tiene un botón para mandar un error de prueba.

9. Backup automático diario

Todos los días a las 12:00 UTC (~8:00 hora de Chile), un cron job de Postgres (pg_cron) llama a la Edge Function backup-diario, que junta TODAS las tablas reales, las comprime (gzip) y las manda por email vía Resend como adjunto .json.gz — sin depender de que la app esté abierta en ningún navegador. La clave de Resend vive cifrada en Supabase Vault, nunca en el código.

Lo que decidimos NO hacer (y por qué)

  • No convertir a módulos ES: cambiar a type="module" cambia reglas de JavaScript en miles de líneas a la vez — mucho riesgo para cero beneficio real hoy.
  • No backend propio: solo se justifica si aparece una razón concreta (una regla de negocio que RLS no pueda expresar, un secreto que ni RLS proteja, pasos que necesiten reintentos transaccionales reales). Hoy no existe esa razón.
